# 株バトル 設計書（長期運用前提）

最終更新: 2026-09-25 ／ リポジトリ: `ksaga115/KabuBattle` ／ 対戦エンジンの流用元: [`ksaga115/BarcodeTool`](https://github.com/ksaga115/BarcodeTool) の `docs/コードバトル設計.md`

日本株（まず日経 225）の **決算 → 素体**、**株価の動き → 日々の状態**、**事業・技術 → 技** の 3 層でキャラクターを組み立て、
コードバトルの対戦エンジンで戦わせる。契約金は株価、手放すと時価で戻る。毎朝の予想がバフになり、夕方に日替わりの相手と戦う。

このドキュメントは「1 年後も 3 年後も壊れずに回り続ける」ことを最優先に書く。面白さの数式は後から何度でも直せるが、
データの流れ・ID・保存形式・移行手順は最初に決めておかないと直せない。

## 0. 貫く柱（変えない）

1. **3 層の分離**。素体（決算、四半期更新）／状態（株価、毎日更新）／技（事業、ほぼ固定）は別ファイル・別更新周期。片方が壊れても他は動く。
2. **ゲームは静的ファイルだけで動く**。`KabuBattle.html` は JSON を読むだけ。サーバーもログインも無い。JSON が古ければ「古いデータで遊ぶ」だけで、壊れない。
3. **データ更新は GitHub Actions が自動で回す**。Claude のセッションにも、あなたの操作にも依存しない。止まったら GitHub からメールが来る。
4. **銘柄の ID は証券コード（4 桁 + 将来の英字対応）**。名前・業種・所属指数が変わっても ID は変えない。
5. **Pay-to-win なし・課金なし・通信は GitHub への静的取得のみ**。株価は本物だが、動くお金はゲーム内通貨だけ。
6. **セーブは端末内（localStorage）＋ JSON 書き出し**。スキーマは版番号を持ち、旧版は 1 世代残す（コードバトルと同じ流儀）。

## 0.1 リポジトリ構成（BarcodeTool から独立）

- 株バトルは **独立したリポジトリ `KabuBattle`** で開発・運用する。データの日次コミットが BarcodeTool の履歴を汚さないため、また GitHub Pages・Actions・Secrets を株バトル専用に持つため。
- 対戦エンジン（コードバトルの `CB`）は BarcodeTool 側が原本。株バトルは **ビルド時に BarcodeTool の特定コミットから `BarcodeTool.html` を取得して抽出**する（`scripts/build-kabu.mjs`。`vendor/BarcodeTool.commit` にコミット ID を固定。更新は手動で ID を進める）。エンジンに手を入れる必要が出たら BarcodeTool 側に後方互換で入れ、株バトルは ID を進めて追従する。
- 公開 URL は `https://ksaga115.github.io/KabuBattle/`（Pages を main の `/` から配信）。

## 0.2 この環境の制約（判明済み）

- Claude Code の実行環境（この作業用コンテナ）からは外部サイト（stooq / J-Quants / JPX / Yahoo）への通信が**ネットワークポリシーで拒否**される。
  → **データ取得は Claude のルーティンではなく GitHub Actions で行う**（ランナーは外に出られる）。この設計はその前提で書く。
- Actions のワークフローファイルを Claude がプッシュできない場合（GitHub App の権限）は、ファイルを用意してあなたが 1 回コミットする。
- GitHub App はリポジトリの新規作成ができない（403）。リポジトリ作成はあなたが行い、Claude はその後にプッシュする。

### 2.1 失敗時の挙動（重要）

- **1 銘柄の取得失敗**: 前回の値を引き継ぎ `stale: N`（連続失敗日数）を付ける。ゲーム側は `stale ≥ 3` で「消息不明」表示、対戦には前回の状態で出る。
- **全体の失敗**（stooq 停止など）: `latest.json` を更新しない。ワークフローは失敗として終了 → GitHub から通知メール。ゲームは「最終更新: 9/25」と表示して前回データで動く。
- **休場日**: 取得はしても新しい行が無い → `marketOpen:false` として `latest.json` の日付だけ進める。ゲームは「今日は休場。対戦相手は前営業日の主役」と扱う。
- **J-Quants 失敗**: 素体は前回のまま。決算の更新は遅れても困らない。
- **異常値**（終値が前日比 ±60% 超で出来高異常なし、など）: その銘柄だけ `suspect:true` にして前回値を使う。株式分割（§8.3）は別途検出する。

### 2.2 秘密情報

- `JQUANTS_REFRESH_TOKEN` は GitHub Secrets のみ。ワークフローの中で ID トークンに交換して使う。
- 画像生成 API キーは Claude のセッションに一時的に渡すだけ（コミットしない・ログに出さない）。
- ゲーム本体は秘密情報を一切持たない。

```json
      "name": "トヨタ自動車", "short": "トヨタ", "sector33": "輸送用機器",

      "addedAt": "2026-09-25", "delistedAt": null, "renamedFrom": []
```

- `elem` は §4.3 の対応表から**機械的に**決める（手で変えない。変えたい時は対応表を変える）。

## 4. 素体（決算 → ステータス）

### 4.1 元データ（`fin/<code>.json`、直近 5 四半期の TTM = 直近 4 四半期合計）

売上高 `sales`、営業利益 `op`、純利益 `ni`、総資産 `assets`、純資産 `equity`、自己資本比率 `eqRatio`、現預金 `cash`、
EPS、BPS、年間配当 `div`、発行済株式数 `shares`、前年同期比の売上成長率 `salesGrowth`、
直近 4 期の営業利益率の標準偏差 `opmStd`（安定性）。金融業は営業利益が無いので `op := 経常利益`。

### 4.2 ステータス（各 24〜100 の整数。コードバトルと同じレンジ・同じ 5 種）

「同じ業種の中でどの位置か」ではなく**全上場企業の中での位置**を対数で正規化する（業種ごとの得意不得意が属性として残るように）。

```
lognorm(x, lo, hi) = clamp((ln(x) - ln(lo)) / (ln(hi) - ln(lo)), 0, 1)      // 対数で 0..1
S(v)               = round(24 + 76 * v)                                      // 24..100

体力 HP  : v = lognorm(時価総額, 200億, 40兆)                                // 時価総額 = 終値 × 発行済株式数（毎日更新）
攻  ATK  : v = 0.65 * lognorm(op(TTM), 10億, 5兆) + 0.35 * clamp((salesGrowth + 0.10) / 0.40, 0, 1)
守  DEF  : v = 0.70 * clamp((eqRatio - 0.10) / 0.70, 0, 1) + 0.30 * lognorm(cash / 総負債, 0.02, 2.0)
速  SPD  : v = clamp((sales / assets - 0.2) / 1.8, 0, 1)                     // 総資産回転率 0.2..2.0
技  TEC  : v = clamp((op / sales - 0.00) / 0.45, 0, 1)                       // 営業利益率 0..45%
運  LUK  : v = 0.5 * clamp(ROE / 0.30, 0, 1) + 0.5 * (1 - clamp(opmStd / 0.08, 0, 1))
```

- 金融業（銀行・証券・保険）は `eqRatio` と回転率が構造的に低い。**業種別の下駄**は履かせない（＝金融は「守が低く見えるが体力が大きい」キャラになる）。代わりに属性の相性で活きる場所を作る（§4.3）。
- `HP` だけは毎日変わる（時価総額）。他の 4 つは決算更新でしか変わらない。
- **決算更新は「生まれ変わり」ではなく「成長/衰え」として見せる**: 更新前後の差分を図鑑に「決算で 攻 +4 守 −2」と残す（§9.2）。

### 4.3 属性（33 業種 → 5 属性。コードバトルの 5 すくみをそのまま使う）

コードバトルの `affinity()` を変更せずに使う。**属性名はコードバトル v7 で陰陽五行（木火土金水）に改称済み**なので、
この設計書が当初書いていた「機甲/烈火/深水/雷電/聖光」ではなく五行の名前を使う。倍率は
相生（生む・d=1）×1.05 ／ **相克（克す・d=2）×1.13** ／ 被克（d=3）×0.89 ／ 被生（d=4）×0.95。

割り当ては、下の覚える一文の「強い」が**相克（もっとも有利な d=2）**になるように並べる。
そうすると本物の五行相克（木剋土・土剋水・水剋火・火剋金・金剋木）とちょうど一致する。

| 属性 | 33 業種 | 相場での役どころ | 克す先 |
|---|---|---|---|
| 木 | 輸送用機器・機械・鉄鋼・非鉄金属・金属製品・精密機器・建設業・ゴム製品 | 景気敏感・製造 | 土（素材） |
| 土 | 化学・石油石炭・鉱業・ガラス土石・パルプ紙・電気ガス・繊維製品 | 素材・エネルギー | 水（生活） |
| 水 | 食料品・水産農林・医薬品・小売業・卸売業・サービス業・陸運・海運・空運・倉庫 | 生活・物流 | 火（情報） |
| 火 | 電気機器・情報通信・その他製品（ゲーム等） | 情報・半導体 | 金（金融） |
| 金 | 銀行・証券・保険・その他金融・不動産 | 金融 | 木（製造） |

覚える一文: **「製造は素材に強く、素材は生活に強く、生活は情報に強く、情報は金融に強く、金融は製造に強い」**。
（相場のローテーション「金利上昇→金融が製造を食う」「半導体→金融が資金を回す」の雰囲気を借りる。厳密さより覚えやすさ。）

土＝素材、水＝物流、火＝半導体、金＝金融と語義も噛み合う。対応表は `src/kabu-core.js` の `SECTOR_ELEM`
（表記ゆれは `SECTOR_ALIAS` が吸収する）。`scripts/kabu/sim.mjs` の 1 節がこの一致を毎回確かめている。

### 4.4 レア度

```
scale  = lognorm(sales(TTM), 10億, 30兆)
quality= clamp(op/sales / 0.30, 0, 1)
rare   = 0.6 * scale + 0.4 * quality     → SS ≥ 0.72 / S ≥ 0.60 / A ≥ 0.50 / B ≥ 0.38 / C ≥ 0.26 / D
```
小さくても利益率が異常に高い企業（キーエンス、ヒロセ電機のような）が A〜S に食い込むように 0.4 を quality に振る。

**下限と閾値は東証の内国株式 3,526 銘柄の実データで測り直した値（2026-09-26）。**
当初は下限 100 億円・閾値 0.85/0.72/0.58/0.44/0.30 だったが、実際の上場企業は売上の中央値が
339 億円・下位 25% が 99 億円以下で、**下位 4 分の 1 が全員 scale = 0** に潰れていた。
結果は SS 0.1% / S 0.5% / A 2.3% / B 8.0% / C 20.1% / **D 69.1%** で、図鑑の 7 割が同じ D になっていた。

下限を 10 億円に下げ、閾値を実測の分位に合わせた結果:
**SS 1.0% / S 3.7% / A 8.5% / B 20.8% / C 31.5% / D 34.4%**。
キーエンス・信越化学・ディスコ・東京エレクトロンが SS、利益率 7% のトヨタは S になる
（利益率に 0.4 を振る配分は変えていないので、上の意図どおり）。

### 4.5 特性（trait）

コードバトルの特性語彙（`fang` `wall` `calc` `luck` `curse` `venom` `regen` `focus` `serene` …）を決算の事実から決定論的に付ける。1 体 1〜2 個。

| 条件 | 特性 | 意味 |
|---|---|---|
| 営業利益率 ≥ 25% | `calc`（貫通） | 高付加価値 |
| 自己資本比率 ≥ 60% | `wall`（守） | 無借金体質 |
| 売上成長率 ≥ 15% | `fang`（攻） | 成長企業 |
| 配当利回り ≥ 3.5% | `regen`（回復） | 株主還元 |
| 直近 4 期の利益ブレが大きい（opmStd ≥ 6pt） | `luck`（振れ） | 業績が読めない |
| 純利益が赤字 | `curse`（呪詛） | 追い詰められた者の逆襲 |
| 総資産回転率 ≥ 1.5 | `focus`（先手） | 身軽 |
| 時価総額上位 10 | `serene`（静養） | 大御所 |

## 5. 状態（株価 → 日々のコンディション）

`fetch-prices.mjs` が計算して `latest.json` に焼き込む派生値（ゲームは計算しない）:

```
chg1     = close / prevClose - 1                 // 前日比
chgYtd   = close / closeAtYearStart - 1          // 年初来騰落率（年初の最初の営業日の終値基準）
ytdPos   = (close - ytdLow) / (ytdHigh - ytdLow) // 年初来レンジの位置 0..1（レンジ幅 0 なら 0.5）
volRatio = volume / avg(volume, 20日)            // 出来高比
range    = (high - low) / prevClose              // 当日の値幅
dev25    = close / sma25 - 1                     // 25 日線乖離
limitUp / limitDown                              // 値幅制限に到達（値幅制限表から判定）
per, pbr                                         // close / EPS(TTM), close / BPS
sectorPer, sectorPbr                             // 同属性の中央値
nk225Chg                                          // 日経平均の前日比（全体イベント用）
```

### 5.1 状態 → 対戦への効き方（すべて**素体に対する係数**、素体は書き換えない）

| 状態 | 条件 | 効果（対戦時のみ） |
|---|---|---|
| テンション | `chg1` | 攻 ×(1 + clamp(chg1, −0.08, +0.08) × 1.5)、守 ×(1 − 同 × 1.0)。上げた日は攻寄り、下げた日は守寄り。**合計は概ね保存**（強弱ではなく配分） |
| 覚醒 | `ytdPos ≥ 0.9` | 全ステ ×1.06、必殺技解放（§6.4） |
| 逆境 | `ytdPos ≤ 0.1` | 体力 ×0.90、会心率 +8pt（「反発の芽」） |
| 勢い | `chgYtd` | 行動順に `+ clamp(chgYtd, −0.3, +0.3) × 20`（年初来 +30% なら速 +6 相当） |
| 注目 | `volRatio` | 攻 ×clamp(0.9 + 0.1 × volRatio, 0.9, 1.25) |
| 荒れ | `range` | ダメージ振れ幅 `spread` に `+ clamp(range × 2, 0, 0.12)` |
| 暴走 | `dev25 ≥ +0.12` | 攻 ×1.12、守 ×0.85 |
| 冬眠 | `dev25 ≤ −0.12` | 速 ×0.85、守 ×1.12 |
| 粘り | `per < sectorPer × 0.7 かつ pbr < 1` | 被ダメ ×0.92 |
| 期待 | `per > sectorPer × 1.5` | 行動順 +10、被ダメ ×1.08 |
| ストップ高 | `limitUp` | 必殺技解放 + 会心率 +10pt |
| ストップ安 | `limitDown` | 初手を必ず休む（行動不能 1 ターン） |
| 暴落の日 | `nk225Chg ≤ −0.03` | **全員**守 ×0.9（相手も）。演出は画面全体が赤 |
| 祭りの日 | `nk225Chg ≥ +0.03` | 全員 攻 ×1.05 |
| 決算日 | `calendar` で当日 | 「覚醒 or 暴走」ボス日（§9.3） |
| 配当落ち | `calendar` で当日 | 体力 ×(1 − 配当利回り × 2)（最大 −10%） |
| 消息不明 | `stale ≥ 3` | 状態係数をすべて 1.0（素体のまま）。図鑑にマーク |

係数の積は **0.75〜1.35 の範囲に clamp** する（状態が素体を覆い尽くさない。「学べば読める」を守る）。

## 6. 技（事業・技術 → moves.json）

### 6.1 構成（1 銘柄 4 つ）

| 枠 | 出どころ | 例（トヨタ） |
|---|---|---|
| 業種技 | 33 業種で共通（`moves.json` の `sector` 節） | 「量産ライン」 |
| 固有技 1 | その企業の事業・技術（Claude が執筆） | 「ジャストインタイム」 |
| 固有技 2 | 同上 | 「カイゼン」 |
| 必殺技 | 同上。**解放条件を満たした日だけ**選択肢に入る | 「全固体電池」 |

### 6.2 効果の語彙（エンジン側。ここに無い効果は作らない）

コードバトル v3 の `kind`（strike / crit / pierce / drain / finisher）を拡張する。技は「kind + パラメータ + 属性」の組で、名前と説明文は自由。

| kind | 効果 | パラメータ |
|---|---|---|
| strike | 素直な一撃 | `pow` |
| crit | 会心率 +N pt | `pow, critAdd` |
| pierce | 守を追加で N% 無視 | `pow, pierce` |
| drain | 与ダメの N% を回復 | `pow, drain` |
| multi | 2〜N 回の連撃（回数は乱数） | `pow, min, max` |
| sure | 必中・バフデバフ無視・威力低め | `pow` |
| first | 使った次のターン必ず先手 | `pow` |
| stack | 使うたび攻 +N（最大 M 回） | `pow, add, cap` |
| gamble | 威力 0〜N 倍の乱数 | `maxMult` |
| delay | N ターン後に大ダメージ（発動前に倒れると不発） | `pow, turns` |
| shield | 味方（自分）に被ダメ −N% を M ターン | `cut, turns` |
| reflect | 次の被弾を N% 反射 | `ratio` |
| swap | 相手の攻と守を入れ替える | — |
| dot | 毎ターン最大 HP の N% を M ターン | `rate, turns` |
| debuff | 相手の 守/速/攻 のいずれか −N% | `stat, cut, turns` |
| heal | 自分の HP を N% 回復（攻撃しない） | `rate` |
| counter | このターン回避に専念。回避できたら反撃 | `pow` |
| finisher | 瀕死時のみ。威力 ×N | `mult` |

エンジンの自動選択（`chooseMove`）は「相手属性への有利 × 期待威力 × 状況（HP・ターン数・バフ有無）」でスコア付けして選ぶ。プレイヤーは技を選ばない（全自動の柱を守る）。

### 6.3 moves.json の形

```json
{
  "schemaVersion": 1,
  "sector": { "輸送用機器": { "name": "量産ライン", "kind": "multi", "min": 2, "max": 3, "pow": 0.6, "text": "同じ品質のものを大量に叩き出す" } },
  "stocks": {
    "7203": {
      "moves": [
        { "name": "ジャストインタイム", "kind": "first", "pow": 0.9, "text": "必要な物を必要な時に。次のターンは必ず先手", "origin": "トヨタ生産方式の柱のひとつ" },
        { "name": "カイゼン", "kind": "stack", "pow": 0.8, "add": 6, "cap": 4, "text": "使うたび攻が積み上がる", "origin": "現場の小さな改善を積み重ねる文化" }
      ],
      "ultimate": { "name": "全固体電池", "kind": "delay", "pow": 2.6, "turns": 1, "text": "1 ターン溜めて大爆発", "origin": "次世代電池の本命として開発中", "unlock": ["awaken", "limitUp", "earnings"] },
      "author": "claude", "reviewed": false
    }
  }
}
```

- `origin`（元ネタの一言）は図鑑に出す。遊ぶほど企業に詳しくなる。
- `reviewed:false` は「Claude が書いた初版」。あなたが直したら `true` にして、以後の自動生成で上書きしない。
- 固有技が無い銘柄（新規追加直後）は業種技 ×2 で代用し、図鑑に「技は準備中」と出す。

### 6.4 必殺技の解放条件（`unlock`）

`awaken`（年初来高値圏）／`limitUp`（ストップ高）／`earnings`（決算日）／`streak`（予想 3 連勝中、§7.3）のいずれか。当日だけ。

## 7. ゲームループ

### 7.1 1 日の流れ（JST）

| 時刻 | 何が起きるか | 誰が |
|---|---|---|
| 〜9:00 | 「今日の予想」を入れる（任意）。パーティ各キャラに 上/下 | あなた |
| 16:30 | 日足取得 → `latest.json` 更新 → Pages 反映（数分） | Actions |
| 夕方以降 | ゲームを開く → 予想の答え合わせ → 通貨付与 → 日替わり対戦（自動） → 結果 | ゲーム（端末内） |

- ゲームは「開いた時に、未処理の営業日をまとめて処理」する（3 日開かなくても 3 日分の対戦と精算が順に走る。処理は `latest.json` の日付と `daily/` の履歴で行うので、**開かなかった日も後から再現できる**）。
- 日次処理の乱数シードは `hash(date, code)`。いつ開いても同じ結果。

### 7.2 通貨と契約

- 通貨「資金」。初期 30 万。
- **契約金 = その日の終値（1 口 = 1 株相当）**。契約は 1 口単位、上限なし。
- **手放すと当日終値 × 口数が戻る**（手数料なし）。
- 稼ぎ: 日替わり対戦の勝利（相手の強さに応じて 500〜5000）、予想的中（1 体 300、パーティ全的中でボーナス）、シーズン報酬。
- 「口数」は株式分割で自動調整（§8.3）。
- 分散投資に自然なインセンティブ: パーティは 3 体（前/中/後）、属性がばらけると共鳴ボーナス（コードバトルの `reso` を流用: 同属性 3 体は「集中投資」で攻 +6% 被ダメ +5%、3 属性ばらばらは「分散」で被ダメ −5%）。

### 7.3 予想（任意・毎朝）

- パーティの各キャラに「上がる／下がる／しない」。終値の前日比 ±0.3% 以内は「引き分け」（外れ扱いにしない）。
- 的中: 会心率 +6pt（その日の対戦）。外れ: 初手怯み（行動順 −15）。
- 連勝カウンター `streak` は銘柄ごと。3 連勝で必殺技解放（§6.4）。
- **Claude の予想**: `latest.json` に「Claude の上/下」を含めない（Actions では Claude を呼ばない・費用ゼロを守る）。代わりに「機械の予想」= 単純ルール（25 日線の上なら上、下なら下）を敵陣営の予想とし、勝率を並べて表示する。将来 Claude を呼ぶなら週 1 のワークフローに限定する。

### 7.4 日替わり対戦

- 相手パーティは `latest.json` の「主役」から決定論的に生成: 値上がり率 1 位、値下がり率 1 位、出来高比 1 位（同一なら次点）。**その日の相場そのものが敵**。
- 相手の強さは自パーティの平均レア度に合わせて素体を ±10% でスケール（コードバトルのガントレットと同じ「梯子」方式）。
- 勝敗はコードバトルの `squadMatch`（2 本先取）。演出も流用。
- 週末・休場日は対戦なし（前営業日の結果を再表示）。

### 7.5 シーズンと称号

- 月＝1 シーズン。勝ち点（勝 3・引 1）と予想的中数で順位帯を決め、称号を付与（「億り人」「塩漬け仙人」「材料株ハンター」「配当長者」…）。称号は図鑑に永続。
- 過去シーズンの成績は `store.seasons[]` に残す（軽量）。

## 8. 長期運用で必ず起きること、その扱い

### 8.1 決算更新（年 4 回）
- `fin/<code>.json` が更新されたら素体を再計算。差分を `store.history[code]` に「2026Q2: 攻 +4 守 −2」で記録。図鑑で見られる。
- 更新は週次ワークフローが担当。ゲームは `latest.json` の `fiscalId` が変わったことで気づく。

### 8.2 日経 225 の入替（3 月・9 月・臨時）
- 入る銘柄: `universe.json` に追加 → 決算取得 → 技は業種技のみ・画像は仮 → Claude が後追いで固有技と画像を足す（`reviewed:false`）。
- 出る銘柄: `indices` から外すだけ。契約中なら持ち続けられる。相手パーティの候補（主役）からは外れる。
- 入替情報の自動取得は不安定なので、**半年に 1 回、手で `build-universe.mjs` を回す**運用も許容する。

### 8.3 株式分割・併合
- stooq は分割調整済み系列だが、**当日〜翌日は未調整で来ることがある**。検出: `chg1` が `1/n − 1`（n = 2,3,4,5,10）または `n − 1` に ±2% で一致し、かつ出来高が平時の 3 倍以上 → `split: n` を立て、その日の「テンション」「荒れ」判定を無効化。
- 契約中の口数を `× n`（併合は `÷ n`）。契約金の基準（取得単価）も同じ比で調整。**資金価値は保存される**。
- 1 週間後に系列が調整済みになったら、`daily/` の過去スナップショットは触らない（監査用にそのまま）。

### 8.4 上場廃止・社名変更・証券コード変更
- 上場廃止: `listed:false`。契約中なら**最終終値で自動的に手放し**、図鑑に「旅立ち」記録（画像はグレー、称号「思い出」）。
- 社名変更: `renamedFrom` に旧名を積む。ID は不変。
- コード変更（稀）: `universe.json` に `movedTo` を書き、セーブの移行時に付け替える。

### 8.5 データが止まった時
- 日次ワークフロー失敗 → GitHub のメール通知。ゲームは最終更新日を表示し、その日までの結果で遊べる。
- 3 営業日以上止まったら、ゲームのトップに「データ更新が止まっています（最終 9/25）」を出す。復旧後は未処理日を順に精算する（§7.1）。
- stooq が使えなくなった場合の代替は J-Quants の有料プラン（月 1,650 円で前日分の日足）か、Yahoo Finance の非公式 API。`fetch-prices.mjs` はソースを差し替えられる構造（`sources/stooq.mjs` / `sources/jquants.mjs` の関数を切り替え）にしておく。

### 8.6 スキーマ変更
- すべての JSON に `schemaVersion`。ゲームは自分が知っている版だけ読み、未知の版は「アプリを更新してください」。
- セーブ `kabu_battle_v1` → 変更時は `_v2` に昇格し `_v1` を残す（コードバトル S7 と同じ）。
- `latest.json` の互換性ルール: **フィールドは追加のみ・削除と意味変更は版を上げる**。

### 8.7 リポジトリの肥大化
- `daily/` は 1 日 60KB × 250 日 = 年 15MB。5 年で 75MB。許容範囲だが、年末に `daily/2026/` へ移動して `daily/2026.jsonl.gz` に固める年次ジョブを用意する（ゲームは `latest.json` と直近 60 日しか読まないので影響なし）。
- 画像は 1 枚 ≤ 60KB（256×256 PNG、ドット絵なら 8bit パレットで 10KB 台）。300 枚で 20MB 以下。

### 8.8 コスト
- GitHub Actions: 公開リポジトリは無料。日次 2 分 + 週次 5 分。
- 画像生成: 一度きり数百〜千数百円（225 枚）。以後は入替の数枚のみ。
- Claude: 技の執筆と入替対応。定期実行では呼ばない。
- **恒常費用ゼロ**を維持する。

## 10. 実装の流用と差し替え

- コードバトルの `CB` から流用: `battle` / `squadBattle` / `match` / `squadMatch` / `affinity` / `squadAura` / 演出 / 図鑑 UI / バックアップ。
- 差し替え: `build()`（コードから個体生成）→ `buildFromStock(universe, fin, state, moves)`。**戻り値の形（`{name, elem, stats, traits, moves, hash, …}`）は CB の個体と互換**にして、対戦関数に無改造で渡す。
- 追加: 技 kind の拡張（§6.2）は CB 側の `chooseMove` / `hit` に足す。`index.html` はビルドで BarcodeTool の固定コミットから CB を抽出して組み込む（BarcodeTool の `QRTransfer.html` と同じ方式: `scripts/build-kabu.mjs`）。CB の改修が必要な分は BarcodeTool 側に後方互換で入れる（既存の個体・対戦結果は不変。シムで確認）。
- 画像が無い銘柄は手続き生成の SVG（属性色 + 業種アイコン + 社名 2 文字）で代用。

## 14. 実装で設計書から変えたこと（2026-09-26）

書いた時点の前提が実際には成り立たなかった点と、その置き換え。**理由が消えないよう、元の記述は取り消し線で残す。**

### 14.1 stooq が使えない → Yahoo Finance

stooq の CSV エンドポイント（`stooq.com` / `stooq.pl` とも）は、JavaScript のプルーフオブワーク型ボット検査を
返すようになっていた。ブラウザ相当の User-Agent でも同じ。**検査の突破はしない**方針で、§8.5 が代替として
挙げていた Yahoo Finance のチャート API に差し替えた。

- `scripts/kabu/sources/yahoo.mjs` … 日足・分割イベント・配当イベント
- 分割は前日比からの推測（§8.3）より **Yahoo が返す分割イベントを優先**する。推測ロジック（`KB.detectSplit`）は
  他のソースに差し替えたときのために残してあり、シムで検証もしている。

### 14.2 J-Quants に届かない → Yahoo fundamentals-timeseries

`api.jquants.com` は**存在しないパスもルートも含めて全パスが 403**（API Gateway のリソースポリシー）。
トークンの正否とは無関係にこの回線からは叩けない。GitHub Actions のランナーからなら通る可能性はあるが、
確かめられないものに M3 を預けない。

代わりに Yahoo の `fundamentals-timeseries`（認証・キー不要）を使う。実測では
年次がほぼ全社 4 期ぶん揃い、四半期は銘柄により疎、`trailing`（TTM）もある。そこで
**TTM は trailing → 四半期 4 期の合計 → 直近年次**、**貸借は四半期 → 年次**の順に埋める
（`scripts/kabu/sources/yahoo-fin.mjs`。どこから採ったかは `ttm.sources` に残す）。
金融業で営業利益が無い銘柄は税引前利益で代用する（§4.1 の「op := 経常利益」に相当。99 銘柄中 14 件）。

J-Quants が使える環境なら `sources/jquants.mjs` を足して差し替えればよい（§8.5 の構造はそのまま）。

### 14.3 日経 225 の名簿が取れない → 東証の内国株式すべてを収録

日経公式の構成銘柄ページは 403、Wikipedia はレート制限で、**225 の名簿だけがどこからも取れなかった**。
一方 JPX の「東証上場銘柄一覧」には全上場銘柄の市場区分・規模区分が入っている。これは一次情報なので、
**東証に上場している内国株式すべて（2026-08-31 時点で 3,535 銘柄）**を収録する（当初は §13-3 のとおり
日経 225 で開始する想定だった）。

- `indices` には市場区分（`prime` / `standard` / `growth`）と規模区分（`core30` / `large70` / `mid400` /
  `small1` / `small2`）を写す。日経のページに届いた時だけ `nk225` を足す（届かなければ据え置き）
- 一度入った銘柄は指数から外れても、上場廃止になっても消さない（§8.2・§8.4 のまま）
- `universe.json` は **1 銘柄 1 行**で書き出す。3,500 銘柄を整形して書くと 3MB を超えて差分も読めなくなる。
  1 行 1 銘柄なら「どの銘柄の何が変わったか」が git の差分でそのまま見え、大きさも 706KB に収まる
- `--large-only` で Core30 + Large70 の 99 銘柄に絞れる（動作確認用）

属性の分布は業種の構成をそのまま映して偏る（実測 水 1381 / 火 872 / 木 636 / 土 356 / 金 290）。
サービス業・小売業・卸売業が水に集まるためで、**§3 の「elem は対応表から機械的に決める」に従い手当てはしない**。
偏りを変えたくなったら個別の銘柄ではなく §4.3 の対応表を変えること。

### 14.3.1 規模が変わったことで必要になった作り直し

3,500 銘柄はゲームの作りを変えるほどの量なので、以下を設計書の本文どおりに戻した。

- **素体を `latest.json` に焼き込む**。§1 はもともと「ゲームが読むのは latest.json・universe.json・
  moves.json だけ。決算の生データはゲームには不要（Actions が素体ステータスまで計算して焼き込む）」と
  書いていたが、実装は銘柄ごとの `fin/<code>.json` をゲームが全部取りに行っていた。99 なら動くが 3,500 では
  破綻する。焼き込みに戻し、決算の内訳は図鑑カードを開いた 1 銘柄だけ取りに行く
- **`daily/` は再現に必要な項目だけの薄い形**にする。日次コミットが git 履歴に永久に積まれるので、
  1〜2MB／日では年 300〜450MB になる。§8.7 の年次アーカイブと併せて容量を抑える
- **履歴の目録 `kabu/data/index.json`**。静的配信ではディレクトリ一覧が取れないので、
  どの日の `daily/<date>.json` が実在するかを JSON で置く（§7.1 のまとめ精算に必要）
- **一覧の表示を絞る**。3,500 行を一度に描かない（検索・属性/レア度/規模での絞り込み・上位 N 件表示）
- **今日の主役に流動性の下限を置く**（§7.4）。3,500 銘柄から素で「値上がり率 1 位」を採ると、ほぼ毎日
  数百円の超小型株のストップ高になり、誰も知らない会社ばかりが毎日ボスになる。「その日の相場そのもの」
  という趣旨から外れるので、時価総額 100 億円を下限にした（`KB.MIN_MCAP`）。下限で候補が 3 体に
  足りなくなったら下限を外す＝主役が出せない日は作らない。`protagonists(latest, {minMcap: 0})` で
  設計書どおりの素の挙動に戻せる

レア度（§4.4）の閾値は「全上場企業の中での位置」を前提にしていたので、全上場企業を収録したことで
ようやく前提どおりになる（大型株 99 銘柄だけのときは SS3 / S14 / A41 / B39 / C2 / D0 と A・B に寄っていた）。

### 14.4 エンジン側に無い仕掛け → 落とし込みで動かし、拡張は後で

設計書はエンジンに 2 つの前提を置いていたが、どちらも現行の CB には無い。§0.1 の
「エンジン改修は BarcodeTool 側に後方互換で入れる」に従って直すまでのあいだ、**無改造のエンジンでも
壊れずに動く形**にしてある。

| 設計書 | 現行 CB | いまの扱い |
|---|---|---|
| §4.2 体力 HP（時価総額） | ステータスは攻守速技運の 5 つだけ。`maxHp` は DEF/SPD/total から計算 | 個体に `hpAdd` を載せる。CB が見るようになったら効く（見なければ無視されるだけ）。表示用の体力値は `kabu.hp` |
| §6.2 の 18 種の kind | 効くのは strike / crit / pierce / drain / finisher の 5 種 | `moves.json` には設計どおりの kind を書き、`KB.KIND_FALLBACK` が一番近い挙動に落とす。CB に kind を足したら表から外すだけで `moves.json` は触らなくてよい |

### 14.4.1 全市場に広げて初めて出たデータの壊れ方（2026-09-26）

大型 99 銘柄では一度も起きなかった問題が、3,700 銘柄にすると一気に出た。**取り込み口で弾く**のが原則
（壊れた値が `latest.json` に載ると、体力・レア度・特性・契約中の口数まで波及する）。

| 何が起きたか | 実例 | 対処 |
|---|---|---|
| **証券コードの判定が新方式を落としていた** | 旧 `^\d{4}[0-9A-Z]?$` は「130A」のような**数字 3 桁＋英字**（2024 年以降の新規上場）に当たらず、**172 銘柄が丸ごと漏れていた** | `^\d{3}[0-9A-Z]$`（4 文字ちょうど）に統一。`build-universe.mjs`・`validate.mjs` の両方 |
| **種類株式・優先株式が普通株に混ざる** | 「ソフトバンク第１回社債型種類株式」など 5 文字コード 7 件。うち 2 件が時価総額 362 兆・182 兆円で `mcapTop10` を占め、ソニーグループを押し出していた | 同じコード判定で除外。実質は社債・優先出資で、キャラクターにする対象ではない |
| **取得元が桁の壊れた終値を返す** | `1909` 16,280,000,512 円/株、`2180` 1,886,167,168 円、`7426` 240,292,736 円。`7426.T` は `meta.chartPreviousClose` まで一貫して壊れており、**meta との突き合わせでは検出できない** | 絶対値の上限で弾く。日本株の実測分位は中央値 1,514 円・99.9% でも 79,600 円なので、100 万円超は `suspect`（§2.1 の扱い） |
| **常識外の分割比** | `1:4,400,000`。契約中の口数と取得単価に直接効く | 実在する分割・併合は 1:10〜10:1 の範囲（§8.3 が挙げる n も 2,3,4,5,10）。範囲外は `splits` に載せない |

前日比が 0 付近のまま絶対値だけ壊れる形なので、**§2.1 の「±60% 超」検査では一件も捕まらない**。
値域の検査は「変化率」と「絶対値」の両方が要る。

### 14.4.2 焼き込みの照合が順序の不具合を捕まえた

`validate.mjs` は、`latest.json` に焼き込まれた素体が `KB.buildFromStock` の再計算と一致するかを
毎回見ている。この検査が、**決算を取る前に素体を焼き込んでいた**という順序の不具合を実際に検出した
（新方式コードの 165 銘柄が、`fin/130A.json` が存在するのに `provisional: true` / レア度 C で
焼かれていた）。焼き込みは速さのための二重持ちなので、**二重持ちが食い違っていないことを機械で
確かめ続ける**のが条件になる。

### 14.4.3 決算発表日は四半期の格子から推定する

設計書 §2 は決算発表予定日を J-Quants `/fins/announcement` から取る前提で、取れない銘柄は
「前回発表日 + 3 か月」で推定するとしていた。J-Quants には届かない（§14.2）ので推定だけで組む。

最初は「`fiscalId`（決算期末）+ 40 日」としたが、これは誤りだった。**取得元は銘柄によって
四半期を配信しておらず、実測では 3,693 銘柄中 2,288 銘柄（62%）の `fiscalId` が年度末で止まる**。
「+ 40 日」だと、この 62% は年 1 回しか決算日が立たない。

`fiscalId` を「直近の四半期末」ではなく**「ある期末」**として読み、そこから 3 か月刻みで四半期の
格子を作れば解ける。四半期末しか取れない銘柄でも年 4 回の発表日が出るし、四半期が取れる銘柄と
まったく同じ格子になる（＝取得元の粗さに結果が依存しない）。帯は**四半期末 + 35〜45 日**
（決算短信の開示は法令上 45 日以内、実際は 35〜45 日に集中する）。

```
3 月期末の会社 → 2/4-2/14・5/5-5/15・8/4-8/14・11/4-11/14（年 44 日）
5 月期末の会社 → 1/4-1/14・4/4-4/14・7/5-7/15・10/5-10/15
```

日本の決算発表シーズンそのものになる。9 月下旬のような谷間は 0 件で、それが正しい。
判定が `(日付, その銘柄の fiscalId)` だけで決まるのが肝心で、こうしておけば焼き込みと
再計算が必ず一致する（§14.4.2）。取得をいつ回したかに依存する条件を混ぜてはいけない。

### 14.5 JSON Schema ファイルは置かなかった（§15 は末尾）

§1 は `kabu/schema/*.json` を置く構成だったが、検証器を別に書くとスキーマと検証が必ずずれる。
`scripts/kabu/validate.mjs` そのものを唯一の規定にし、依存パッケージも増やしていない。

### 14.6 対戦の演出

コードバトルの演出は CB エンジンではなく BarcodeTool の画面側にある。抽出しているのはエンジンだけなので、
再生は**エンジンが組み立てたログ文面をそのまま色分けして出す**形にした（技名・ダメージ・会心・属性有利は
エンジンが `log[].m` に入れてくれている）。HP バーのアニメーションなどは未着手。

## 15. 気質・ポートフォリオ・練度（2026-09-27）

### なぜ足したか

実際に 120〜200 日遊ばせて測ったところ（`scripts/kabu/playtest.mjs`）、**全銘柄そろえた後にやることが無い**
ことがはっきりした。素体は四半期に 1 回しか動かず、状態は当日の断片だけ。一方で**日足を 1 年ぶん取って
いるのに、使っていたのは前日比・年初来位置・出来高比・25 日線乖離だけ**だった。時系列そのもの＝テクニカル
の情報をまるごと捨てていた。

足すものは**実在の指標に限る**。架空の強化値は入れない。

### 15.1 気質（テクニカル）— 銘柄ごとの性格

日足 1 年から計算する。**追加の通信は要らない**（すでに 1 年ぶん取っている）。決算（四半期）より速く、
株価（毎日）より遅く変わる。`fetch-prices.mjs` が `latest.json` の各銘柄に `tech` として焼き込む。

実測（東証 120 銘柄）での散らばり:

| 指標 | 10% | 中央 | 90% | 両端の実例 |
|---|---|---|---|---|
| ヒストリカル・ボラティリティ（年率） | 19.2% | 29.5% | 53.7% | 浜木綿 10.9% ↔ テクニスコ 122.3% |
| ベータ（日経への感応度） | 0.06 | 0.22 | 0.71 | 片倉コープアグリ −0.23 ↔ 扶桑化学 1.34 |
| 自己相関（1 日ラグ） | −0.16 | −0.03 | 0.10 | ピープル −0.30 ↔ シード +0.26 |
| 最大ドローダウン | −45.2% | −23.7% | −12.8% | |
| 売買代金（60 日平均） | 0.04 億 | 0.56 億 | 31 億円/日 | 776 倍 |

対戦への効き方（すべて `stateMods` の係数。素体は書き換えない）:

| 気質 | 効き方 | なぜそうなるか |
|---|---|---|
| ボラティリティ | 高いほど **運寄り**（運 ×1.25 / 技 ×0.80 まで）、低いほど技寄り | CB は振れ幅を運と技から決める（`spread = 0.17 × (1 + 運/100×0.95 − 技/100×0.70)`）。運と技を傾けることが、そのままボラティリティの再現になる |
| ベータ | **暴落の日・祭りの日の効果が β 倍** | 設計書 §5.1 は全員一律 ×0.9 / ×1.05 としていたが、実際の付き合い方は銘柄ごとにまるで違う。市場と逆に動く銘柄すらある |
| 自己相関 | モメンタム型は前日の動きが続く向きに攻が動く。平均回帰型は下げた翌日に会心 +5pt | 「勢いが続く株」と「行き過ぎたら戻る株」という実在の性格 |
| 最大ドローダウン + 回復 | 3 割超下げて高値圏の 9 割まで戻した銘柄は **不屈**（一度 HP1 で耐える） | 「一度沈んだが立て直した」という事実 |
| 売買代金 | **行動順** ±12 | 薄い銘柄は動き出しが鈍い |

### 15.2 ポートフォリオ — その日の編成（やりこみの軸）

**全銘柄持っていても、今日の相場に対する最適な 3 体は毎日変わる。** ここが収集が終わった後も残る意思決定。

- **隊のベータ** = 3 体の β の平均。暴落の日は低 β の隊が耐え、祭りの日は高 β の隊が伸びる
- **3 体の相関**。現実の分散投資は「業種が違う」ことではなく「値動きが連動しない」こと。
  3 体ぶんの日次リターンを持たせるのは重すぎる（3,700 銘柄 × 250 日）ので、**実在の一ファクターモデル**で
  見積もる: 2 銘柄の相関 ≒（それぞれの市場との相関の積）＋ 同業種なら +0.30 ／ 同属性なら +0.10。
  使うのは焼き込んだ `corr` と業種だけなので、セーブとは無関係に決まる
  - 相関 ≤ 0.15 → **分散の共鳴**（被ダメ −5%）
  - 相関 ≥ 0.45 → **集中投資**（攻 +6% 被ダメ +5%）
- 五行の散らばりは**相性**（攻撃の有利不利）を担当し、相関は**分散**を担当する。役割が分かれる（§7.2 の
  「同属性 3 体は集中投資、3 属性ばらばらは分散」を、値動きの実態で測る形に置き換えた）

### 15.3 練度 — 不正のできない成長

現実の「長く持つほど成績のブレが縮む（時間分散）」をそのまま持ち込む。**CB には熟練度（mastery 0〜5、
効果は「その個体のダメージの振れを 2%/段、最大 −10% 縮める。素のステータスは上げない」）が既にあり、
`squadOf` が常に 0 を渡していた。** ここに保有営業日数を繋ぐ。エンジンの改修は要らない。

```
練度 = clamp(floor(log2(保有営業日数 + 1)), 0, 5)   ただし「これまでに精算した日数」で頭打ち
```

- 素のステータスは上げないので、持ち続けても弱い銘柄が強い銘柄を追い越さない（§0 の Pay-to-win なしと同じ）
- 伸びるのは「安定して戦えること」だけ
- 手放すと練度は消える（保有していないのだから当然）

### 15.4 不正ができないこと

**個体差の源泉をすべて公開データに置く。** 気質・ポートフォリオ・素体・レア度・特性・状態は、
`universe.json` / `latest.json` / `fin/` から決まる。セーブを書き換えても 1 ミリも動かない。

セーブ側にあるのは「あなたが何をいつ選んだか」（契約・編成・予想）と、そこから積み上がる練度だけ。
練度は**精算した日にしか増えず、これまでに精算した日数を超えられない**ので、数字を書き換えても
`masteryOf` が切り捨てる。

やり残し: 契約の履歴そのものを決定ログにして、資金・口数・取得単価まで公開データから再計算する形
（買値はその日の終値に固定されているので、資金を書き換える不正が原理的に効かなくなる）。
対人でパーティを見せ合うときに、受け取った側が履歴の整合性を検証できるようになる。

## 16. 一人で遊ぶ中身（2026-09-27）

### なぜ足したか

「一人で楽しめる要素が少なすぎる」。そのとおりで、1 日にやることは**予想を 3 つ選んで精算を押すだけ**、
30 秒で終わっていた。しかも毎日まったく同じ手順で、選ぶ理由も変わらない。

架空の要素は足さない。**実在の投資でやっていることを、そのまま毎日の中身にする。**

### 16.1 今日のお題

毎日ひとつ、**実在の投資スタイル**がお題として出る。条件を満たす 3 体で勝つと 30,000 円。
日付だけで決まる（`hash(date)`）ので、いつ開いても同じお題。

| お題 | 条件 | 該当する銘柄（実測・3,693 銘柄中） |
|---|---|---|
| バリュー投資 | PER 15 倍以下 かつ PBR 1 倍以下 | 829 件（22.4%） |
| グロース投資 | 売上成長率 15% 以上 | 759 件（20.6%） |
| 高配当 | 配当利回り 3% 以上 | 1,185 件（32.1%） |
| ディフェンシブ | ベータ 0.5 以下 | 2,816 件（76.3%） |
| 小型株 | 時価総額 500 億円以下 | 2,342 件（63.4%） |
| 高収益 | 営業利益率 20% 以上 | 377 件（10.2%） |
| 無借金経営 | 自己資本比率 60% 以上 | 1,566 件（42.4%） |
| 順張り | 年初来レンジの上位 20% | 712 件（19.3%） |
| 逆張り | 年初来レンジの下位 20% | 703 件（19.0%） |
| 大型・高流動 | 売買代金 10 億円/日 以上 | 644 件（17.4%） |
| 低ボラティリティ | 値動きの荒さ 20% 以下 | 579 件（15.7%） |
| 再生 | 3 割超下げて高値圏の 9 割まで戻した | 106 件（2.9%） |

- **条件を満たすことと強いことは別**。低ボラティリティの隊は技寄りで安定するが、攻めは立たない。
  お題を取りに行くと勝ちにくくなる、というのが選択になる
- 判定は `latest.json` に焼き込んだ値だけで完結する（ゲームは銘柄ごとの決算ファイルを一括では
  読まないので、売上成長率・営業利益率・自己資本比率の 3 つを `fund` として載せた。1 銘柄 20 バイト）
- 市場の絞り込みに「今日のお題だけ」を足したので、条件に合う銘柄を探すところから遊べる
- 12 種類すべて達成すると全制覇

### 16.2 日経平均に勝てているか

初めて精算した日の総資産と日経平均を覚えておいて、**そこからの伸びを指数と比べる**。
実在の投資でいちばん見られる指標で、毎日変わり、しかも簡単には勝てない。

```
あなたの運用 +12.4%   日経平均 +8.1%   日経に勝っています +4.3 pt
```
